# feiqiu-r 架构设计

> 本文档记录整体架构、分层契约,以及与参考项目 [box-im(盒子IM)](https://github.com/bluexsx/box-im)
> 的对照。**核心差异:box-im 是 C/S + 服务器集群模型;feiqiu-r 是纯 P2P 局域网模型,没有服务器。**

---

## 1. 分层总览

```text
┌──────────────────────────────────────────────────────────────┐
│ apps/desktop  (Tauri v2 + React/TS)      apps/fq-cli          │
│   React 视图层  ⇄  Tauri commands / fq://event  ⇄  REPL        │
└───────────────────────────┬──────────────────────────────────┘
                            │ 只依赖 fq-core 的稳定 API
┌───────────────────────────▼──────────────────────────────────┐
│ fq-core  应用核心(业务编排,对应 box-im 的 im-platform)       │
│   身份装配 · 事件泵 · 会话/未读 · 回执 · 离线队列 · 群组扇出    │
└──────┬──────────────────────────────────┬────────────────────┘
       │                                  │
┌──────▼──────────────┐        ┌──────────▼───────────────────┐
│ fq-store            │        │ fq-net                        │
│ SQLite 本地优先存储  │        │ 传输层(对应 box-im im-server)│
│ 消息/会话/群组/队列  │        │ UDP 发现 · TCP+Noise · 扇出   │
└─────────────────────┘        └──────────┬───────────────────┘
                                          │
                               ┌──────────▼───────────────────┐
                               │ fq-crypto  fq-proto          │
                               │ 身份/Noise  报文/分帧/兼容    │
                               └──────────────────────────────┘
```

**依赖方向严格单向**:`fq-proto` ← `fq-crypto` ← `fq-net` ← `fq-core` ← apps。
跨层只能向下依赖;协议层零 IO、零网络、零存储,保证可单测到穷尽。

## 2. 与 box-im 的对照

| 维度 | box-im(参考) | feiqiu-r(本项目) | 说明 |
|---|---|---|---|
| 拓扑 | C/S:客户端 ⇄ im-platform(HTTP)+ im-server(WS) | **纯 P2P**:局域网节点直连 | 无服务器是产品前提(内网/离线可用) |
| 业务与推送分离 | ✅ platform / server 两服务 | ✅ fq-core / fq-net 两 crate | 相同的分层哲学 |
| 跨节点路由 | Redis List 队列 + serverId 路由 | **不需要**:P2P 直连;跨网段用 bootstrap/中继(规划) | 拓扑决定的差异 |
| 消息持久化 | 服务端 MySQL + 客户端 IndexedDB/SQLite | **仅本地 SQLite**(本地优先) | 无服务器 ⇒ 无服务端历史;离线消息靠发送方队列 |
| 在线状态 | 服务端连接态 | UDP 心跳 + 超时清扫 | 等价能力 |
| 离线消息 | 服务端存储,上线拉取 | **发送方本地队列入队 → 对端上线自动补发** | 关键差异见 §4 |
| 未读/会话 | 服务端会话表 + 客户端本地表 | 本地 `conversations` 表(未读数 + 预览 + 已读位点) | 本轮补齐 |
| 消息状态 | 发送中/已发送/已送达/已读 | `pending/sent/delivered/read`(回执驱动) | 本轮补齐 |
| 群聊 | 服务端群表 + 消息扇出 | **本地群 + 发送方扇出**,接收方自动建群 | 无服务器的一致性代价见 §5 |
| 多设备同步 | 服务端同步 | 未实现(每个数据目录即一个身份) | 规划中 |
| 音视频 | WebRTC(原生) | 未实现 | 规划中 |
| 分页/搜索 | 服务端分页 + 搜索 | 本地 `history_before` 分页 + `LIKE` 全文搜索 | 等价能力 |

## 3. 分层契约(强制)

| 层 | 允许做的事 | 禁止做的事 |
|---|---|---|
| `fq-proto` | 报文编解码、分帧、能力协商 | 任何 IO、任何 `NodeId` 之外的外部依赖 |
| `fq-crypto` | 身份、握手、信任固定 | 网络收发、存储 |
| `fq-net` | 发现、连接、传输、去重、传输会话 | 业务语义(不解释"未读""会话") |
| `fq-store` | 哑存储(SQL/字符串) | 感知协议类型(不 import fq-proto) |
| `fq-core` | 编排:身份装配、事件泵、会话/未读、回执、队列、群扇出 | 直接操作 socket / SQL 细节 |
| apps | 展示与交互 | 绕过 fq-core 直接调 fq-net 的业务语义 |

**可替换性验收**:GUI 换成 CLI 只改 apps;协议换成 IPMSG 只加 adapter crate(网络层只依赖 trait)。

## 4. 消息可靠性模型(本地优先)

```text
发送方                                    接收方
  │ ① 落库(status=pending)                 │
  │ ② 直发成功 → status=sent               │
  │    直发失败 → 入 pending 队列表          │
  │ ③ 收到 Delivered 回执 → status=delivered│ ④ 收到即落库 + 回 Delivered
  │ ⑤ 收到 Read 回执 → status=read         │ ⑥ 用户打开会话 → 回 Read + 清未读
  │                                         │
  └─ 重试时钟:队列非空 → 每秒重试,直到收到回执出队(上限 10 分钟)
```

* **恰好一次**:UUIDv7 消息 ID + 接收端去重窗口;重发无副作用
* **出队依据是回执**,不是"交给连接"(连接可能中途死掉,消息会蒸发)
* 群聊例外:扇出无法逐条对账,不做回执(成本/收益取舍,见 §5)

## 5. 群聊的 P2P 一致性问题(已知取舍)

没有服务器 ⇒ 没有权威成员表。当前策略:

1. 建群方本地定义成员;发消息时**逐成员单播**(带 `group_id` + `group_name`)
2. 接收方**自动建群**并把发送者补进成员(群名随消息带来)
3. 离线成员的消息**按成员入队**,上线补发

**代价(诚实记录)**:
* 成员表可能发散(接受者知道 A 和 B,但不知道 C)——因为成员表是从消息里"看到谁在说话"逐渐增长的
* 群消息无回执(UI 无 ✓/✓✓)
* 没有群主/踢人/成员同步协议

**演进方向**:引入"群主节点 + 成员表同步报文"(P2P 也能做,只是需要一次设计),或成员表随消息全量携带(小群可行)。

## 6. 数据模型(SQLite,`fq-store`)

```sql
messages(id PK, peer, is_outgoing, from_node, kind, body, format,
         ts_ms, created_ms, delivered_ms, read_ms, reply_to, recalled)
         -- kind: text | image | file;peer 为 NodeId hex 或 group:xxx
         -- reply_to:引用回复指向的消息 ID(只存 ID,正文各端从本地历史取)
         -- recalled:已撤回标记(保留原条目,渲染成一行提示)
conversations(peer PK, last_msg_ms, preview, last_read_ms, unread, pinned, muted)
         -- 会话列表:置顶优先 + 活跃排序 + 未读持久化(重启不复活);muted 只留小点
peers(node_id PK, display_name, host_name, group_name, first_seen_ms, last_seen_ms)
         -- 联系人列表:由发现驱动(删掉的人再发现就回来,见 §8.4)
pending_messages(id, peer, envelope BLOB, queued_ms, PK(id, peer))
         -- 离线队列(原始报文);PK 含 peer —— 群消息同一个 ID 要分别排给多个成员
groups(id PK, name, members CSV, created_ms)  -- 本地群定义
transfers(token PK, peer, direction, path, size, status, detail,
          started_ms, finished_ms)           -- 传输历史(v5)
peer_avatars(node_id PK, sha256, mime, data BLOB, updated_ms)  -- 对端头像缓存(v6)
```

迁移采用 **`PRAGMA user_version` 逐级升级**(v0→v1→…→v11),
每一步都有回归测试(`v1_database_migrates_to_latest_schema` 等),老数据文件永远可打开。
`peer_avatars` 只缓存**校验通过**的头像:离线联系人也能显示头像(摘要里带回缓存哈希)。
**v2 的 `hidden_peers` 已在 v7 删除**:删除联系人不再走"永久隐藏",改为飞秋语义(见 §8.4)。
v8 给会话加 `pinned` / `muted`(置顶排序、免打扰只留小点),v9 给消息加 `reply_to`(引用回复),
v10 加 `recalled`(消息撤回),v11 把待发队列主键改成 `(id, peer)`(群消息一个 ID 投递给多人)。

## 8. 版本管理(约定)

**单一来源**:根 `Cargo.toml` 的 `[workspace.package].version`。
其余两处由脚本同步(Rust 侧 `env!("CARGO_PKG_VERSION")`、前端 Vite `define` 都指向它):

| 文件 | 用途 |
|---|---|
| `Cargo.toml` | 全部 crate 的版本;关于页显示 |
| `apps/desktop/frontend/package.json` | Vite 注入 `__APP_VERSION__`(联系人 NEW 标签) |
| `apps/desktop/tauri.conf.json` | 安装包文件名 + Windows 资源版本 + 在线通告广播 |

**升级规则**(每次改动按幅度执行,一条命令):

```powershell
.\scripts\bump-version.ps1 -Bump patch   # 修 bug / 文案 / 样式微调   0.2.0 → 0.2.1
.\scripts\bump-version.ps1 -Bump minor   # 新增功能 / 交互改进        0.2.0 → 0.3.0
.\scripts\bump-version.ps1 -Bump major   # 协议不兼容 / 数据迁移       0.2.0 → 1.0.0
```

**为什么必须同步三处**:版本号会随在线通告广播,用于局域网 P2P 更新发现
(§见 `check_update`)。若三处不一致,会出现"安装包名是 0.2.0、关于页显示 0.1.0、
对端 NEW 标签误报"这类矛盾。脚本是唯一的改版入口,不要手改单处。

### 8.1 自动更新(P2P 拉取安装,无更新服务器)

沿用"不做公网依赖"的定位,更新包**由局域网内版本更高的节点直接提供**:

```
老版本 A                                   新版本 B(v9.9.9,运行 fq-desktop.exe)
  │  1. 在线通告携带 app_version → A 发现 B 更高
  │  2. Kind::UpdateRequest{requester_version}  ───────────────►  版本比较:
  │                                                                  local > requester ?
  │  3.        ◄──── Kind::UpdateOffer{version, manifest}      是 → 提供 current_exe()
  │  (自动接收,无需用户确认;走既有 Noise 加密传输 + 256 KiB 分块)
  │  4. 接收完成 → SHA-256 与发送方 FileDone 声明比对 → UpdatePackageReady 事件
  │  5. 安装:延迟批处理等待本进程退出 → copy /Y 覆盖自身 exe → 重启 → 自删
  ▼
```

设计要点与取舍:

| 点 | 做法 | 理由 |
|---|---|---|
| 传输通道 | 复用文件传输会话(不新增传输实现) | 分块/续传/校验/进度已测 |
| 信任 | 仅接受**版本更高**且 TOFU 已固定的对端;Noise IK 认证发送方 | 无需额外签名体系,LAN 内可信 |
| 完整性 | 接收方对整包做 SHA-256 校验,不匹配即中止 | 传输损坏/截断不会装成坏包 |
| 用户裁决 | 设置里 `auto_update`:关闭(默认)= 一键询问;开启 = 自动下载 + 10 秒倒计时重启 | 覆盖安装=重启应用,给一次反悔机会 |
| 服务端来源 | 新版本节点提供本机可执行文件(`current_exe`,可用 `--serve-package`/`AppConfig.update_package` 指定) | exe 自带前端资源,单文件即完整版本 |
| 降级防护 | 请求方版本 ≥ 本机版本时拒绝提供 | 避免被诱导降级 |
| 安装护栏 | ① 必须位于本机下载目录内(规范化后比较,防 `..`)② 必须 `.exe` ③ 必须与本机程序**同名** ④ 必须带 `MZ` 头 | 即使 UI 被注入,也无法把本机替换成任意文件;也能挡住"局域网里 跑着构建产物 fq-cli.exe"的误覆盖 |
| Windows 覆盖 | 运行中 exe 被锁 → 生成 `%TEMP%\fq-update-*.cmd`:等待退出 → **备份 `.bak`** → copy(失败重试) → start → 自删 | 不引入额外更新器组件;`.bak` 即回滚点(下次更新时覆盖) |
| 可观测性 | 桌面端写文件日志 `<数据目录>/logs/fq-desktop.<日期>.log`(保留 7 天) | GUI 子进程没有控制台,日志是唯一排查线索 |

**实测结论**(2026-09-23):两台进程实机跑通 老版本→自动索取→自动接收 14.7 MB→SHA-256 校验
→10 秒倒计时→覆盖自身 exe→自动重启(进程 PID 变化);同名冲突时就绪事件正确上报换名后的
实际路径;更新脚本执行完自删,`.bak` 回滚点生成。

**踩坑记录**:`profile.json` 若带 UTF-8 BOM(记事本、`PowerShell Set-Content -Encoding UTF8` 都会写),
`serde_json` 直接解析失败 → 配置**静默回退默认值**(表现为"自动更新开关不生效、下载目录被重置")。
现在 `load_profile` 会剥离 BOM 并记录警告;`save_profile` 明确写无 BOM UTF-8。

已知限制:若安装目录需要管理员权限(如 Program Files),覆盖会失败并重试到超时 ——
此时用户可手动安装;NSIS 默认装到 `%LOCALAPPDATA%\Programs`,该问题不会出现。

### 8.2 资料同步(昵称 / 分组 / 头像)

昵称与分组随**在线通告**(`PresenceInfo`)广播,改完立即通告(`PresenceEvent::Update`),
对端联系人列表几秒内更新 —— 零额外协议。

头像则不放进通告:UDP 数据报装不下(会被 IP 分片,广播还浪费带宽),只在通告里放
**64 字节哈希**;`avatar_request` / `avatar_reply` 走 TCP 加密通道按需传整图。

| 设计点 | 做法 | 理由 |
|---|---|---|
| 本地头像 | 固定文件 `<数据目录>/avatar.png`,桌面端用 `image` crate 统一裁成 256×256 方图 | 文件名固定 → 无需配置项;压缩后约 20~80 KB |
| 变更检测 | 通告带哈希;`PeerTable` 的变化检测**包含** `avatar_sha256`/`app_version`/`capabilities` | 曾漏掉:只改头像不产生 `PeerUpdated` → 对端永远拿不到新头像(已加回归测试) |
| **发起方确定** | 只有 **NodeId 较小**的一方主动拉取;较大方 15s 后兜底 | **踩坑**:双方同时拨号时后建连接会替换旧连接,RST 掉在途报文 → "同步重拨"互相打断,头像 17s 都到不了 |
| **一次往返双向同步** | `avatar_request` 里捎上自己的头像(`mine`) | 于是"我改头像"不需要对端也拨号:一次请求两个方向都同步 |
| 变更即推送 | `reload_avatar()` 通告后**主动推**给所有在线且支持头像的对端 | 否则等兜底 15s,用户以为对方看不到 |
| 重试 | 退避 1s→2s→3s→6s(≤12 次)+ 按 NodeId 派生抖动 | 撞车后自动错开;实测收敛从 17s 降到 **1.2s**(8/8 稳定) |
| 移除头像 | 通告 `avatar_sha256=null` → 对端**清缓存**并发 `PeerAvatarRemoved` | 否则对方界面一直显示旧头像 |
| 能力协商 | 仅对声明 `AVATAR`(位 8)的对端收发 | 老版本节点不会被无谓打扰 |
| 完整性 | 接收方校验 `sha256(data)`(请求捎带的同样校验) | 与文件传输同级的校验强度 |
| 展示 | 前端 `get_peer_avatar` 拉 base64 缓存,事件触发重取;**离线联系人用缓存哈希照常显示** | 不在事件里塞大 payload |

界面配套:左侧图标栏头像可点(进个人资料设置),设置页「个人资料」可改昵称/分组/头像,
联系人、最近会话、聊天头部统一显示头像(没有头像时回退首字母色块)。

**实测**(2026-09-23):桌面端 ↔ CLI 真实进程,互知后 **1~3 秒**完成头像双向同步
(SHA-256 校验通过、落库、离线可显示)。

> 同机双实例注意事项:两个进程都绑定 UDP `24250` 时,Windows 会把**单播**通告只投给
> 其中一个 socket(广播才会都收到),因此新启动的一侧可能要等对方 20s 心跳广播才"看见"它。
> 这是同机演示的固有现象(真实环境每机一实例,单播直达),排查时表现为
> `入站连接的静态密钥没有对应已知对端,拒绝` + `known=[]`(等心跳即可恢复)。

### 8.3 联系人删除语义(飞秋式:发现驱动)

**删除 ≠ 永久隐藏**。列表由局域网发现驱动,删除只是"当前从列表移出":

| 动作 | 效果 |
|---|---|
| 右键「从列表移出」 | 删联系人行 + **忘记网络层对端表里的它**(`forget_peer`)+ UI 立即摘掉;聊天记录、会话、头像缓存全部保留 |
| 对方下一次通告 | 因为对端表里已没有它,这次通告走 `Discovered` → 重新入库 → 自动回到列表 |
| 点「刷新」 | 广播 3 轮通告 + 等回发(约 0.7s)→ `refresh_contacts` 把已知对端**全部写回**列表,包括刚删掉的人 |
| 「已删 N / 恢复」按钮 | **已移除**(不再需要恢复,局域网里有就会自己回来) |

两个实现要点(都是踩坑换来的):

1. **必须 `forget_peer`**:只删数据库行的话,网络层对端表里还有它 → 心跳不产生"变化"事件
   → `on_peer_seen` 不再被调用 → 联系人永远回不来。
2. **刷新要有人回话**:已知对端收到 `Announce` 时,单播回一发 `Update`(用 `Update` 而非
   `Announce` 是为了避免双方互相回发;心跳 `Heartbeat` 不触发,不做无谓流量)。
   否则"刷新"要等对方 20s 心跳才生效。

### 8.4 联系人面板交互

| 项 | 做法 |
|---|---|
| 分区折叠 | 「最近会话」「群聊」标题可点,折叠状态存 `localStorage`(重启记住) |

## 11. 0.9.0 新增机制(设计要点)

| 机制 | 关键设计 | 为什么这样做 |
|---|---|---|
| **传输失败自动重试** | `fq-core` 事件泵只在**发送方向**且失败原因可重试时(中断/超时/分块或完成通知发不出去)重新发起,上限 `SEND_RETRY_MAX = 2`、间隔 2s;重试沿用同一行传输历史(token 改名),并上报 `TransferRetrying` / `TransferRetryGaveUp` | 瞬断是局域网里最常见的问题。取消、对端拒绝、哈希校验失败**不**重试 —— 重来一遍不会有不同结果,只会打扰对方(系统错误文案里的"积极拒绝"≠对端拒绝,分类器按更具体的短语匹配) |
| **网段直扫发现** | `fq_net::subnet_scan_targets` 枚举每个本机 IPv4 所在 /24 的其余主机(去重、不扫自己);`App::scan_subnet` 逐地址单播通告(2ms 间隔);启动 3s 后自动扫一次(仅通配绑定),设置页与 CLI `/scan` 可手动触发 | 广播常被交换机/安全软件拦掉,`bootstrap` 又要手填 IP。单播探测是幂等小包,未运行本程序的主机不会响应,代价可以忽略 |
| **界面主题(跟随系统/浅色/深色)** | 模式存 `profile.json`;生效结果由 JS 写到 `<html data-dark="true|false">`,CSS 中所有暗色规则从 `@media (prefers-color-scheme: dark)` 机械改写为 `[data-dark="true"]` 作用域 | 手选主题必须能与系统不一致,媒体查询表达不了"手动覆盖"。启动早期先读 localStorage 缓存,避免"先白后黑"闪屏 |

## 12. 0.10.0 新增机制:消息撤回

| 决策 | 做法 | 为什么 |
|---|---|---|
| **只传消息 ID** | `RecallBody { message_id }`;两端各自在本地历史里标记 `recalled` | 与引用回复同一思路:不复制正文,协议不膨胀,历史只是"这条没了" |
| **越权校验在接收侧** | 收到 `recall` 时比对「这条消息的 `from_node`」与「撤回报文来源」,不一致即忽略并告警 | 撤回必须只有发送方能做;不能信任报文里自称的身份 |
| **时限在发送侧** | `RECALL_WINDOW_MS = 2 分钟`,超时直接报错(UI 也同步隐藏菜单项) | 超时撤回会让对端历史"回退",体感比不能撤回更糟 |
| **群消息共用一个 ID** | `send_group_text` 扇出时所有副本复用同一个 `MsgId` 与 `ts_ms`,本地群历史也用这个 ID | 每个成员各存各的 ID 时,撤回无法定位对方那份副本(本版踩过并修正) |
| **离线也撤回** | 撤回报文走与文本相同的"可达即发、不可达入队",不额外重试 | 对方上线后必须看不到已撤正文,否则撤回等于没做 |
| **撤回后仍保留条目** | 不删行,只置 `recalled`;若该条恰是会话最新消息,`preview` 改 `[已撤回]` | 删行会让历史时间线错位、ID 复用风险高;列表里显示已撤正文则是隐私问题 |
