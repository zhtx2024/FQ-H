### 已知限制:撤回目前只支持文本

文件/图片消息的**发送**侧本地条目用的是新建的消息 ID,而接收侧的文件条目由传输流程
自行生成 —— 两端 ID 不一致,按 ID 撤回无法定位。要支持需要把消息 ID 随文件要约一起
传(`FileOffer` 加字段),留到后续版本;**群文件**同理。`kind != "text"` 的菜单项已隐藏。

### 取舍理由(群成员同步 / 消息撤回 / 语音)

| 候选 | 价值 | 成本 | 结论 |
|---|---|---|---|
| **消息撤回** | 高(发错消息是日常高频场景,且"发出去就收不回"在局域网 IM 里体感最差) | 中(新增一个协议报文 + `messages` 加状态列,不动传输与发现层) | ✅ **优先**:价值/成本比最高,且能复用现有回执与事件链路 |
| 群成员同步 | 高(群成员变化目前靠"消息顺带同步",成员不发消息就会滞后) | 大(需要"群主权威 + 版本号 + 冲突合并"一整套设计,还要处理群主离线) | ⏳ 次之:适合作为 0.10 的主线,单独一轮做 |
| 语音消息 | 中(局域网场景里文字+文件已覆盖多数需求;语音还需要麦克风权限、编码、播放 UI) | 大(音频采集/编码/播放 + 传输策略 + 波形 UI) | ⏳ 最后:等前两项稳定后再评估 |

## 已知限制(不计划短期内解决)

- 群消息**不做逐条回执**:扇出无法对账(见 ARCHITECTURE §5)
- 同一台机器跑多实例需手动错开端口,且共享 UDP 发现端口时单播可能落在另一个实例上(见 ARCHITECTURE §8.2 注)
- 自动更新在需要管理员权限的安装目录(如 `Program Files`)会失败并重试到超时;NSIS 默认装到用户目录,不受影响
- 应用未做代码签名,Windows 首次运行会有 SmartScreen 提示
